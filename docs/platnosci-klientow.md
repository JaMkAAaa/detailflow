# #148 — płatność klienta studia (sandbox)

## Zatwierdzony model i granice

29.10.2026 użytkownik zatwierdził przez formularz OpenBot: **studio: Connect Standard + direct charges, prowizja Detailflow 0%**. Studio jest sprzedawcą i odbiorcą środków; ponosi opłaty Stripe, obsługuje zwroty i spory w swoim pełnym Stripe Dashboard. Implementacja nie tworzy destination charges, transferów ani application fee. Stripe Billing abonamentu Detailflow i KSeF pozostają osobnymi obiegami. #110–112 są zamknięte; historyczne „Poza v1” nie blokuje autoryzowanego #148. #115 pozostaje otwarte.

**Wyłącznie sandbox.** Nowy klient SDK akceptuje tylko `sk_test_`, również przy pominiętej walidacji env. Live nie jest wdrożone. Nie deklarujemy prawnej ani produkcyjnej gotowości. Zwrot w Stripe nie cofa automatycznie `paidAt`: oznacza pierwotne otrzymanie płatności; zwrot/spór i korekta wymagają osobnego rozliczenia studia. Nie dodajemy obsługi zwrotów do makiety w tym issue.

## Konfiguracja Stripe krok po kroku

1. W osobnym środowisku **Stripe sandbox** platformy włącz Connect dla SaaS. Potrzebna jest możliwość tworzenia kont **Standard** przez Accounts v1 oraz direct charges. Ustaw nazwę, ikonę i kolor Connect Onboarding. Jeśli Stripe nie udostępnia tej konfiguracji platformie, wymaga to uzgodnienia ze Stripe; nie zastępuj Standard kontami Express/Custom ani destination charges. Accounts v1 `type=standard` jest świadomym wyborem zgodnym z zatwierdzonym modelem; Stripe kieruje nowe platformy także do Accounts v2, ale ten PR nie zmienia zatwierdzonego kontraktu na v2.
2. Sekrety dostarcz bezpiecznym formularzem OpenBot, nigdy w issue/logach: `CLIENT_PAYMENTS_STRIPE_SECRET_KEY=sk_test_…` (klucz platformy Connect sandbox), `CLIENT_PAYMENTS_WEBHOOK_SECRET=whsec_…` (sekret **osobnego** endpointu Connect). `APP_URL` to bazowy URL aplikacji, bez końcowego `/`. W hosted sandbox użyj HTTPS. Klucz publiczny nie jest potrzebny — klient przechodzi na Stripe-hosted Checkout.
3. W Stripe Workbench dodaj snapshot webhook dla **zdarzeń kont połączonych** (Connected accounts), URL `https://<aplikacja>/api/client-payments/webhook`, wersja **2026-09-30.endive** (wspólna ze zainstalowanym stripe SDK 23). Zdarzenia: `checkout.session.completed`, `checkout.session.async_payment_succeeded`. Zachowaj dotychczasowy endpoint Billing `/api/stripe/webhook` i jego sekret bez zmian. Billing ignoruje zdarzenia z `event.account`.
4. Owner studia otwiera `/settings` → „Połącz / dokończ aktywację Stripe”. Backend tworzy konto Standard PL w sandbox, zapisuje unikalne `clientPaymentAccountId`, generuje krótkotrwały jednokrotny Account Link. Link pokazuje się tylko zalogowanemu ownerowi; nie wysyłaj go klientom. Formularz nie przyjmuje ID konta. Ten przepływ zakłada konto tworzone przez tę platformę; podłączanie dowolnego istniejącego konta przez OAuth nie jest zaimplementowane. Jeśli studio chce użyć istniejącego konta, nie wpisuj ID ręcznie — potrzebny jest odrębny, autoryzowany przepływ OAuth.
5. Dokończ onboarding **testowymi** danymi Stripe. Sam powrót do `/settings?connect=return` niczego nie aktywuje. Przy tworzeniu Checkout backend odczytuje konto Stripe i wymaga `type=standard`, metadanych studia, `charges_enabled`, `payouts_enabled` i `card_payments=active`. Po wygaśnięciu linku właściciel ponawia przycisk; konto pozostaje to samo. Odebranie dostępu do konta powoduje bezpieczny błąd Stripe, nigdy fallback do konta platformy.
6. Po migracji schematu w **dedykowanym środowisku testowym** utwórz fakturę do zakończonego zlecenia. W szczegółach faktury (desktop/mobile) użyj „Utwórz link płatności”. Przekaż klientowi otrzymany URL Checkout wybranym kanałem. Ta akcja niczego nie wysyła e-mailem/SMS.

## Kontrakt API i bezpieczeństwo

- `POST /api/studios/:studioId/client-payments/connect`: owner + sesja + Origin + ograniczenia abonamentu + rate limit. Konto tworzone z idempotency key studia; blokada doradcza serializuje onboarding.
- `POST /api/studios/:studioId/invoices/:invoiceId/checkout`: owner/manager + sesja + Origin + rate limit; **puste body**. ID odbiorcy, customer, kwota, waluta i faktura pochodzą wyłącznie z serwera. Płatna, szkicowa/anulowana faktura, korekta, faktura z korektą i niezakończone zlecenie są odrzucane. Faktura i customer są powiązane w obrębie konta studia, nie z customerem abonamentu. Wszystkie zapytania operacyjne przechodzą przez `studioDb(studioId)`; złożony FK eventu wymusza tenant faktury.
- `Decimal` brutto PLN → razy 100 → kontrola całkowitości i zakresu 200–99 999 999 groszy (minimum kartowe PLN 2,00 zł; górny limit tej implementacji 999 999,99 zł) → dopiero `number`. Bez rabatów, kuponów, shipping, podatku Stripe, zmiennej quantity lub kwoty z klienta. VAT już jest w kwocie FV. Metody ograniczone do `allowed_payment_method_types: [card]`; karty muszą być włączone na koncie studia.
- Customer, Checkout i PaymentIntent powstają z `Stripe-Account: <konto studia>`. Metadata Checkout i PaymentIntent: `invoiceId`, `studioId`. Idempotency key osobny dla customer i kolejnych prób Checkout. Otwarta sesja jest ponownie używana, wygasła nieopłacona dostaje nową próbę. Complete/unpaid blokuje nową sesję do rozstrzygnięcia przez Stripe. Błędy sieciowe nie uprawniają do płatności ręcznej.
- `DELETE …/checkout` wygasza otwartą sesję w Stripe i potwierdza `expired/unpaid`. Działa także przy nieaktywnej gotowości konta, jeśli nadal mamy dostęp API. Dopiero potem możliwe oznaczenie przelewu ręcznego lub korekta. Po potwierdzeniu wpłaty online webhookiem można również wystawić korektę księgową; nie generuje ona automatycznego zwrotu Stripe. Zakończonej sesji nie da się anulować w ten sposób.
- Przed zdalnym tworzeniem Checkout zapisywana jest trwała rezerwacja. Nieznany wynik/timeout utrzymuje blokadę manual/correction; ponowienie w ciągu 23 godzin odzyskuje próbę z tym samym idempotency key. Starsza nierozstrzygnięta rezerwacja wymaga operatora i sprawdzenia stanu w Stripe, bez automatycznego czyszczenia flagi lub nowego pobrania: Stripe może usunąć idempotency key po 24 godzinach. To celowe zatrzymanie, nie dowód braku wpłaty.
- Blokada wiersza faktury w transakcji serializuje Checkout, webhook, płatność ręczną i korektę. Manual/correction sprawdza stan bieżącej sesji Stripe. Nie usuwa ID starej sesji i nie uznaje lokalnego czasu wygaśnięcia za dowód.
- Webhook weryfikuje surowe body, podpis i tolerancję czasu; wymaga sandbox i `event.account` zgodnego ze studiem. Sprawdza payload i świeży odczyt Checkout oraz PaymentIntent na właściwym koncie: sessionId, customer, metadata, PLN, identyczna kwota, complete/paid i succeeded, brak prowizji/transferu. Atomowo ustawia `paidAt`, `paymentIntentId` i event deduplikacji. Retry po błędzie nie traci eventu; replay z tym samym lub nowym event ID nie nadpisuje paidAt. Konflikt z manualnym rozliczeniem nie nadpisuje go.
- Publiczny `/payment-result` zawiera tylko ogólną informację; powrót z Checkout nigdy nie ustawia paidAt ani nie ujawnia danych faktury. Link Checkout jest poufny i umożliwia opłacenie konkretnej FV; przekazuj go właściwemu klientowi. Brak dostępu do cudzej FV przez API, nawet znając invoiceId.

## Weryfikacja sandbox i ograniczenia dowodów

Automatyczne testy korzystają z izolowanego PostgreSQL i atrap SDK, rzeczywistego sprawdzania podpisów Stripe oraz istniejących regresji abonamentowych. Nie są dowodem komunikacji z hosted Stripe. Pełny hosted smoke wymaga dwóch kont Standard sandbox, kluczy i webhooku.

Manualny hosted smoke po dostarczeniu sekretów: onboarding dwóch studiów; jedna otwarta sesja mimo ponowienia; kwota brutto PLN i branding właściwego studia w Checkout; testowa karta `4242 4242 4242 4242`, przyszła data, dowolny testowy CVC; płatność widoczna na koncie studia, bez application fee i bez przychodu platformy. Potwierdź paidAt dopiero po podpisanym webhooku Connect. Wyślij ponownie ten sam event przez Workbench i sprawdź niezmienność paidAt. Osobno sprawdź odrzucenie karty, anulowanie/wygaszenie, nową sesję po expiry, manual po potwierdzonym expiry oraz brak dostępu drugiego studia. Sprawdź również działanie istniejącego Checkout abonamentu i osobnego webhooku Billing. Nie używaj realnych kart ani live.

**W tym PR brak kluczy i potwierdzonego hosted sandbox smoke.** Nie uruchamiano realnych opłat, wysyłek ani MF PROD. Wdrożenie migracji i konfiguracja Connect na docelowym środowisku pozostają czynnościami operatora.
